`aweXpect` is a fluent assertion library for .NET. It turns test verifications into readable sentences and produces
failure messages that explain in plain English what was expected and what actually happened.

```csharp
await Expect.That(message).IsEqualTo("It's a compliment");
```

```text title="Failure message"
Expected that message
is equal to "It's a compliment",
but it was "It's a complement", which differs at index 12:
           ↓ (actual)
  "…a complement"
  "…a compliment"
           ↑ (expected)
```

## Why aweXpect?

<Tabs groupId="aweXpectFeatures">
<TabItem value="async" label="Async-first" default>

Every expectation is awaited. The same fluent chain works for sync values, `Task`, `IAsyncEnumerable`, exceptions and
HTTP responses (with the separate [aweXpect.Web](/aweXpect/extensions/aweXpect.Web) package): there is no
parallel `…Async()` API to remember.

```csharp
// Plain value
await Expect.That(result).IsEqualTo(42);

// Task<T>
await Expect.That(_artists.GetAsync(id))
    .Satisfies(a => a.IsActive);

// IAsyncEnumerable<T> - the cancellation token flows through the stream
await Expect.That(_radio.StreamAsync())
    .Contains(s => s.IsLive)
    .WithCancellation(cancellationToken);

// Delegate that throws
await Expect.That(() => _player.SetVolumeAsync(-1))
    .ThrowsExactly<ArgumentOutOfRangeException>();
```

Because the chain is awaited, `Because(...)` and `WithCancellation(...)` attach once at the end instead of being
threaded through every method. Multiple expectations compose directly via `Expect.ThatAll(...)`, without a
thread-static assertion scope.

</TabItem>
<TabItem value="extensible" label="Extensible">

The [`aweXpect.Core`](https://www.nuget.org/packages/aweXpect.Core) package is intentionally kept stable so extensions
don't fight over versions. Ready-made [extension packages](./07-extensions/index.md) cover JSON
([aweXpect.Json](/aweXpect/extensions/aweXpect.Json)), HTTP ([aweXpect.Web](/aweXpect/extensions/aweXpect.Web)),
architecture tests ([aweXpect.Reflection](/aweXpect/extensions/aweXpect.Reflection)), file and time systems
([aweXpect.Testably](/aweXpect/extensions/aweXpect.Testably)) and mocks
([aweXpect.Mockolate](/aweXpect/extensions/aweXpect.Mockolate)).

Add expectations for any other type as extension methods on `IThat<T>`. For a simple condition, a source generator
writes the expectation, its negation and the failure messages for you:

```csharp no-compile
public static partial class ThatTrack
{
    [GenerateExpectation("Is{Not}RadioFriendly", "is {not} radio friendly")]
    private static bool IsRadioFriendly(Track track)
        => track.Duration < TimeSpan.FromMinutes(4);
}

// usage
await Expect.That(track).IsRadioFriendly();
```

The full walkthrough is at [Extending aweXpect](./11-extending/index.md).

</TabItem>

<TabItem value="frameworks" label="Any runner">

```csharp no-compile
[Fact]        // xUnit
[Test]        // NUnit / TUnit
[TestMethod]  // MSTest
public async Task IsActive()
    => await Expect.That(artist.IsActive).IsTrue();
```

xUnit, NUnit, MSTest and TUnit are detected automatically, see the
[supported versions](./08-setup/01-test-frameworks.md): a failure usually throws the assertion exception of the test
framework, see [failed expectations](./08-setup/01-test-frameworks.md#failed-expectations) for the exact types. `Fail`
and `Skip` [fail or skip a test](./08-setup/01-test-frameworks.md#failing-a-test) without an expectation.

## Migrating from another assertion library?

The [aweXpect.Migration](https://github.com/Testably/aweXpect.Migration) analyzer ships code-fix providers that rewrite
most FluentAssertions and `xunit.Assert` call sites for you. See the [migration guide](/aweXpect/migration) for the full
walkthrough.
