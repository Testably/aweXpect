# aweXpect Agent Guide

aweXpect is a .NET assertion library: `aweXpect` ships the expectations, `aweXpect.Core` the engine and the API
for extension packages. The extension packages `aweXpect.Json`, `aweXpect.Web`, `aweXpect.Xml`, `aweXpect.Reflection`
and `aweXpect.Snapshots` (with `.DiffEngine` and `.PublicApi`) live here as well. All packages are released together
to NuGet with one version.

## Setup

- The SDK comes from `global.json` (10.0.3xx). Running the `net8.0` tests also needs the .NET 8 runtime.
- Shared settings live in `Directory.Build.props`, `Source/Directory.Build.props` and `Tests/Directory.Build.props`;
  package versions only in `Directory.Packages.props` (central package management).
- Libraries target `netstandard2.0;net8.0;net10.0` with `TreatWarningsAsErrors`; analyzers and generators target
  `netstandard2.0`; most test projects target `net48;net8.0;net10.0`.
- GitVersion needs the full git history for `./build.ps1` targets that compile (`git fetch --unshallow`).

## Design Goals

Correctness is a must. The other goals are strong defaults and win in this order when they conflict: stable and compatible, AOT and trimming friendly, a consistent and pleasant API, a fast happy path, extensible, errors at compile time, documented. [Docs/agents/design-goals.md](Docs/agents/design-goals.md) explains each goal, the code rules, the checks before a commit and the goals of this repository.

## Project Constraints

- **One version for all packages.** The packages reference each other as projects in every configuration, and a tag
  `vX.Y.Z` releases all of them with the same version. A breaking change in any package waits for the next major.
- **Trimming and Native AOT.** The libraries are `IsTrimmable`/`IsAotCompatible` on `net8.0+`. Reflection is only
  allowed behind `ReflectionFallback.IsSupported` (`Source/aweXpect.Core/Core/Extending/ReflectionFallback.cs`), except
  the type-shape queries that design goal 3 allows; types reach equivalency and event recording through registrations
  generated by `aweXpect.Core.Generators`. Changes in this area must pass `AotSmokeTests`.
- **net48 is a target.** Most test projects also build for `net48`, and `aweXpect.Tests` has no `IsExternalInit` or
  `Index` polyfill, so records and list patterns fail there, on `net48` only. Build `-f net48` first when you use a
  newer language feature.
- **Generated code runs in the consumer's compilation.** Generator output is written for C# 7.3 and qualifies names
  with `global::`.
- **Public API is snapshotted.** Any public surface change must update the snapshots in `Tests/aweXpect.Api.Tests`.
- **Every expectation is documented.** `DocsApiCoverageTests` fails when a public expectation of `aweXpect` or a
  member of `Expect`, `Fail`, `Skip` or `Signaler` is not mentioned in `Docs/pages`, and every `csharp` block there
  must compile (or be marked `csharp no-compile`).
- **Extension packages build on `aweXpect.Core` only**, never on `aweXpect`, and add no new runtime dependencies. When
  an extension needs more from Core, extend Core in the same change. The API conventions of all extensions and the
  goals of each package are in [design-goals](Docs/agents/design-goals.md#extension-packages), its architecture in
  [project-structure](Docs/agents/project-structure.md#extension-packages). The rules that are easy to break:
  - `aweXpect.Xml` parses XML only through `Helpers/SecureXml` (no DTDs, no external resolution).
  - `aweXpect.Reflection` checks `ReflectionFallback.IsSupported` in every method that reflects over a subject, as the
    trim analyzer does not follow the check into a called method or a lambda.
  - `aweXpect.Json` serializes caller values by reflection only behind `ReflectionFallback.IsSupported`.
  - The `buildTransitive` targets of `aweXpect.Snapshots` and `.DiffEngine` run in every consumer build.
    `aweXpect.Snapshots.PublicApi` is not trimmable and must not pull reflection into `aweXpect.Snapshots`.
- **Extension expectations are documented** in `Docs/extensions/<Package>`, including the overview table of its
  `00-index.md`, and in the overview table of the package README `Source/<Package>/README.md`, which links to the docs
  with absolute URLs. These code blocks are not compiled.
- **New analyzer diagnostics** go into the project's `AnalyzerReleases.Unshipped.md`.
- Do not add `#pragma` or other suppressions for analyzer or Sonar findings without asking the maintainer first.

## Validation

- Run the tests of every project your change can affect, not just `aweXpect.Tests` (see
  [testing](Docs/agents/testing.md)). Changes to `[GuaranteesNotNull]` markings need `aweXpect.Analyzers.Tests`.
- The unit and API tests are TUnit executables of the Microsoft.Testing.Platform: start them with `dotnet run`, not
  `dotnet test`. Only the MSTest, NUnit and xUnit v2 projects under `Tests/Frameworks` run with `dotnet test`.
- Slow tests are `[Explicit]` and `[Category(TestCategories.Slow)]` and only run with
  `--treenode-filter "/*/*/*/*[Category=Slow]"`. After any change to `Docs/**`, run them in `aweXpect.Docs.Tests`.
- Test conventions: test methods in alphabetical order within their class; no comments in tests, put the reasoning
  into `.Because(...)`; never a bare `Throws<T>()`, always pin the message with `.WithMessage(...)`; timing tests run
  on a virtual clock with `.WithTimeProvider(new VirtualTimeProvider())` instead of wider margins.
- The SonarCloud quality gate requires all reported issues to be solved and a code coverage above 90%.

## Editing

- The working tree uses CRLF (`.editorconfig`, `core.autocrlf`). `sed -i` and other tools that write LF break the raw
  string literals in tests that pin failure messages. Prefer an editor tool that keeps line endings.
- Many `.cs` files start with a UTF-8 BOM. PowerShell rewrites strip it; check `git diff` for a removed U+FEFF.
- Comments explain why, not what; prefer XML docs.
- No em-dashes in `Docs/**`, XML docs or the changelog.
- `Docs/pages/10-migration/04-from-awexpect-3.md` is the changelog of the upcoming v4: touch it only for important
  changes. The full list of changes is in the GitHub releases.

## Git Workflow

- Work on a branch; PRs target `main` and are squash-merged.
- The PR title follows conventional commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `ci:`, `chore:`, with
  `!` for breaking changes (`feat!:`). Dependency bumps are `chore:`.
- Commit message = PR description: the subject is the PR title, the body explains why. One line per paragraph, no
  hard wrapping, no co-author or attribution trailers.
- Never commit `.claude/` or pending snapshot files (`*.awexpect-snapshot.pending.*`).
